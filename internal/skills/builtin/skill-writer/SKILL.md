# skill-writer

用户要"把这套做法存成技能、写一个 skill、以后同类任务不用再交代一遍、改进或检查已有技能"时先读本技能：技能是写给"以后的你"的操作手册，先把真任务做对，再把验证过的做法沉淀下来。

## 值得写，还是不值得

值得：同一类任务会反复出现，有固定步骤或容易踩的坑；用户明确说"以后都这样做"。

不值得：一次性的问答；通用常识；一句话能说清的个人偏好（那用 `remember` 记进记忆）；还没人验证过的流程。技能写得多不等于好，每一份都要占模型的注意力。

## 放在哪里，谁覆盖谁

| 位置 | 范围 |
| --- | --- |
| `<工作区>/skills/<名字>/SKILL.md`，或 `<工作区>/.cursor/skills/<名字>/SKILL.md` | 这个项目，跟着项目走，团队共享 |
| 数据目录下的 `skills/<名字>/SKILL.md` | 本机所有工作区共用（数据目录的位置在"设置 → 用量与诊断"里看） |
| `AGENTGO_SKILL_DIRS` 指定的文件夹 | 用户额外指定的技能库 |
| `~/.claude/skills`、`~/.agents/skills` 等 | 其他智能体装的技能，设置 `AGENTGO_EXTERNAL_SKILLS` 才会读 |
| 程序内置 | 最后一级 |

同名时，越靠上的越优先。同名覆盖内置技能是允许的（团队可以改措辞），但先 `activate_skill` 读一遍原版，别无意中丢掉规则。数据目录是 AgentGo 自己的目录，你写不进去：个人技能先存到工作区，再请用户把整个文件夹复制过去。

## 文件格式

```
---
name: weekly-report
description: 用户要做销售周报、日报汇总时先读本技能：……
requires:
  bins: [python]
credentials: [SALES_API_TOKEN]
---
# weekly-report

正文……
```

- `name` 不写就用文件夹名；`description` 不写就取正文第一段。front matter 可以整段省掉，第一段当触发条件就行。
- `description` 是**触发条件**，模型只靠它决定要不要加载：写"用户要……时先读本技能"，带上用户真会说的词（"周报""销售汇总""导出明细"），一两句话，别写成内容摘要。
- `requires.bins` 写脚本要用的程序（`python`、`node`、`pwsh`、`bash`），缺了 `activate_skill` 会给出提示。
- `credentials` 只写密钥的**名字**。值在脚本运行时由 AgentGo 从环境变量（或数据目录里的凭据文件）交给那一个脚本，不会进入模型、技能正文或参数。**绝不把密钥、令牌写进 SKILL.md。**

## 正文怎么写

1. 开头一句：这个技能帮谁做什么。
2. 先问清什么：缺的信息一次问完，不要一句一问。
3. 步骤：编号；每步写**调用哪个工具、关键参数、做完看什么**。工具名和参数名照着真实的写，不要凭印象。
4. 验证：怎么判断做对了（读回、对账、再跑一遍）。
5. 边界：做不到的、容易踩的坑，写出原因。不要写"请认真仔细"这类空话。
6. 汇报：做完告诉用户什么。

正文一次最多注入 16000 字节，超过会被截断。写不下就拆：主技能写流程，参考资料放在技能文件夹里的单独文件，正文里写明文件名，用到时再读。技能里的"以后"要具体：写"每月 5 号前"，不要写"定期"。

## 带脚本的技能

脚本放在技能文件夹里（例如 `scripts/build.py`），用 `run_skill_script` 运行：`skill_id` 写 `skill:<名字>`，`script` 写相对技能文件夹的路径，`args` 一词一项。支持 `.py`、`.ps1`、`.js`、`.mjs`、`.sh`、`.bat`、`.cmd`。

- 脚本以工作区为当前目录；技能文件夹路径在环境变量 `AGENTGO_SKILL_DIR` 里，输出文件写到 `AGENTGO_SKILL_OUTPUT_DIR` 指向的文件夹，运行结果会列出这些文件。
- 只有工作区和个人文件夹里的技能能带脚本，内置技能没有。开了 `AGENTGO_SANDBOX_OS` 时这个工具不能用，只能改用 `execute_bash` 运行。
- 脚本要自己处理好错误并打印清楚的原因，退出码非 0 表示失败；不要在脚本里写死路径和密钥。

## 怎么做

1. 先把任务真做一遍并确认结果正确，把用到的步骤、参数和踩过的坑记下来。
2. 用 `evolve_skill` 的 `action` 为 `list` 看已有哪些技能，名字不要撞；要改的是已有技能时，先用 `manage_extension_versions`（`action` 为 `snapshot`，`skills` 填技能名）留一份快照。
3. 起草 SKILL.md。`evolve_skill` 的 `action` 为 `save` 时，`skill_name` 是文件夹名，`code_snippet` 填**完整的** SKILL.md 内容（含 front matter）；`skill_name` 里除英文字母、数字、`-`、`_` 以外的字符会被换成 `-`，全是中文会报 `invalid skill_name`，所以用英文短名，中文名写进 `description`。它保存到 `<工作区>/skills/<skill_name>/SKILL.md`，同名文件会被覆盖。需要脚本或参考文件时，用 `create_workspace_file` 写进同一个文件夹。
4. 保存后用 `activate_skill` 加载一次（`skill_id` 写 `skill:<名字>`）：能加载、`resources` 里有你的脚本、`readiness` 没有缺项。
5. 找一个真实的例子，**只靠这份技能**（不靠当前对话里的上下文）再做一遍；做不对的地方回去改技能，改到不需要口头补充为止。

## 汇报

告诉用户：技能叫什么、存在哪、在什么情况下会被触发、依赖什么程序或密钥、哪些部分验证过、哪些没验证。不要把没跑过的脚本说成"已测试"。
