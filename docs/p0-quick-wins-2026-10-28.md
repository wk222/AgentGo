# 三个 P0：指令文件、一键代码审查、命令资源上限（2026-10-28）

对应 `docs/frontier-agents-gap-2026-10-28.md` 里的三个 P0。结论在前：三项都做完了，已经随 `0.1.0-win7.10` 打包（网页版 + 桌面版，旧 Go 工具链）；有自动化测试，打包时的全量测试通过；代码审查、命令超时、指令文件、工作区外读取都在打好的 exe 上用真实模型（配置里的 `qwen/qwen3.7-max`，临时数据目录）端到端跑过，记录见第 6 节。没有提交。

一个要知道的事：第一次打包（`0.1.0-win7.9`）后复验时发现 `/review` 会漏掉新建文件里的缺陷，所以又改了一轮重新打成 7.10，7.9 的产物已删除，没有发出去过。过程在第 2 节"打包后复验发现的问题"。

## 1. 指令文件兼容

**现在会读哪些文件**（按模型读到的顺序，后读的更具体）

1. 数据目录里的 `AGENTS.md`：用户自己的、对所有工作区都生效的说明。
2. 从 git 根到工作区根，每一层的 `AGENTS.md`；这一层没有就读 `agents.md`，再没有就读 `CLAUDE.md`。
3. 工作区根的 `SOUL.md`、`TEAM.md`（AgentGo 自己的人设和团队文件，和以前一样）。
4. `.cursor/rules`：
   - 没有 front matter、或 `alwaysApply: true` 的，整篇注入；
   - 有 `description` 或 `globs`、但不是 alwaysApply 的，不整篇注入，只在一个索引里占一行，模型觉得任务相关再去读；
   - `alwaysApply: false` 且既没有描述也没有 globs 的，视为手动使用，不提供。

**配置**：`AGENTGO_AGENTSMD_PARENTS`（默认开）。关掉后只读工作区根的文件，不读用户级文件和上层目录。

**实现**：`internal/agent/instruction_files.go`（发现与排序）、`rule_frontmatter.go`（规则头解析，容忍 Cursor 常见的不合法 YAML，比如没加引号的 `*.ts`）、`os_agentsmd.go`（读文件的后端，带路径限制）、`middlewares.go`（接到 Eino 的 agentsmd 中间件）。

**顺手修了三个已有的问题**

- `@` 导入的路径限制其实没生效：`@../../x` 或 `..\x` 能读到允许范围之外。现在只允许项目根目录树和用户级那一个文件，符号链接指到项目外的文件也不读。
- 大小写不敏感的文件系统上，`AGENTS.md` 和 `agents.md` 会被当成两个文件重复加载。
- `@docs/` 这种目录导入会让整个加载失败，进而中止这次运行；现在跳过。

**验证**：`internal/agent/instruction_files_test.go`，包括穿过真实 Eino 中间件的端到端用例（顺序为用户级、根、被导入的、应用层、规则索引；工作区外的 `@../../secret.md` 被拒；`@docs/` 被跳过）。打包后在真实模型上验证过：用户级、仓库根、子目录三层各放一个暗号，模型把三个都原样说了出来（第 6 节）；对长任务行为的影响没有验证。

## 2. 一键代码审查

**怎么用**

- 网页和桌面：输入 `/review`，或在斜杠菜单、欢迎页卡片里点"审查代码变更"。命令后面可以写审查重点，例如 `/review 只看错误处理`。
- 终端界面：`/review [重点]`。
- 对话气泡里只显示你敲的那一行；给模型的说明书折叠在 `<command-instructions>` 标签里（前端 `userText.ts` 负责折叠，复制和"回滚检查点"也只用你敲的那部分）。

**它做什么**：`internal/core/commands.go` 里的 `ExpandCommand` 在 `sendMessageCore`（所有聊天入口的汇合点）把 `/review` 展开成一份审查说明：先调用 `get_workspace_changes`；新建的文件（状态里以 `??` 开头）内容随工具结果一起给，不用再去读；只报这次改动引入的问题（即使问题就在被改动的函数里、只是改名或调格式时碰到了它，也不报）；P0–P3 分级；固定的输出格式（结论、问题、没能核实的部分）；只审查，不改文件。`@` 提及在命令参数里照常展开。

**连带改了 `get_workspace_changes`**（`internal/tools/workspace_changes.go`）

- 增加 `stat`（每个文件改了多少行），diff 被截断时能看出哪些文件被砍了；截断落在行尾、不切断 UTF-8 字符，并提示"带 `path` 再调用一次读剩下的"。
- **新建的、还没 `git add` 的文件，内容直接随结果返回**（`internal/tools/workspace_untracked.go`，输出字段 `untracked`）：每个文件带行号（`=== new file: export.go (13 lines) ===` 加上 `1| ...`），最多 20 个文件、单个文件最多 24 KiB、合计最多 48 KiB，超出的写明文件名和"还有多少没给"；`.gitignore` 排除的不列；二进制文件、符号链接、名字像密钥的文件（`.env`、`*.pem`、`id_rsa`、`credentials*` 等，`.env.example`、`*.pub` 不算）只写一行说明，不把内容给模型；截断落在行尾、不切断 UTF-8 字符。起因见下面"打包后复验发现的问题"。
- 中文文件名不再被转成 `\346\226\207...`。
- **修了一个实际的 bug**：以前把 git 的 stderr 和 stdout 合在一起，开了 `core.autocrlf=true` 的 Windows 机器上，"LF will be replaced by CRLF" 的警告会混进 diff，让模型去审查警告文字。现在只取 stdout。

**验证**

- 单元测试：`internal/core/commands_test.go`、`internal/tools/workspace_changes_test.go`（临时 git 仓库，含中文文件名、autocrlf 警告、截断）、`internal/bridge/context_expander_test.go`、`internal/tui/tui_test.go`、前端 `scripts/user-text.test.cjs`。
- 真实模型，临时仓库 `review-ws`：基线提交里有两个"旧"缺陷（空切片会 panic），工作区改动里新引入两个缺陷（修改过的文件里新增函数 `TopN` 切片多取一个；新建的未跟踪文件 `export.go` 里忽略写文件错误并恒返回 nil），另有一处纯改名。结果：
  - 两个新缺陷都报了，行号对得上（`stats.go:29`、`export.go:11-12`）；
  - 旧缺陷和改名都没报；
  - 结论是"先修完再合入"，"没能核实的部分"老实写了"未运行测试"；
  - 工作区文件前后哈希一致，没改任何文件；
  - 约 82 秒（事件时间戳），没有触发审批；一共调用了 `get_workspace_changes` 一次，另外用代码查看、搜索工具读了新建的未跟踪文件。
- 干净仓库跑 `/review`：17 秒，如实说没有改动，没有转去审查别的代码；`get_workspace_changes` 被重复调用了 3 次，有点浪费，不影响结果。

**打包后复验发现的问题（`0.1.0-win7.9`）和处理**

- 现象：在打好的网页版 exe 上重复跑同一个测试仓库，`/review` 有几次没找到新建文件 `export.go` 里的缺陷（5 次里有 2 次左右，没有逐次记录）——模型没有去读那个文件。说明书里"新文件要自己读"靠模型自觉，不可靠。另外它常把改名那段旁边的旧缺陷（`Max` 对空切片 panic）也报出来。
- 处理：新建文件的内容改成由 `get_workspace_changes` 直接带回（见上面的 `untracked`），说明书里去掉"自己去读"；并写明"即使问题就在被改动的函数里，或者只是改名、调格式时碰到了它，也不报；只有这次改动扩大了影响才报，并写明理由"。
- 复验（`0.1.0-win7.10` 网页版，真实模型，同一测试仓库，共 5 次）：
  - 两个新缺陷 5/5 都找到；有计时的 4 次各用 18–22 秒（改之前约 82 秒）；只调用了 `tool_search` 和 `get_workspace_changes`，不再去读文件；没有审批。
  - `export.go` 的行号准确（工具结果里带行号）。**`stats.go` 的行号不准**：模型报的是 24-27，缺陷实际在第 29 行——这次它没打开那个文件，只能从 diff 的 `@@` 行自己数。以前它读了文件时报的是准确的 29。
  - 旧缺陷：1 次明确写"属于既有缺陷，本次未扩大影响，故不报"；另外 4 次仍把"`Max`/`Average` 对空切片会 panic"列成 P2，理由是新增的 `SaveReport` 直接调用它们、扩大了触发面。按新规则这是允许的，理由也成立（`SaveReport(path, nil)` 确实会 panic），但本质上还是在报旧问题；团队想要更严的口径，说明书需要再收紧。其中一次的 P2 说明里把调用关系说错了（写成 `TopN` 调用了 `Max`/`Average`，其实是 `SaveReport`），结论方向没错。改名本身没有被当成问题报。

**限制**：不是独立的子智能体，在当前会话里运行，所以会占用当前会话的上下文；"只审查不改文件"靠说明书约束，不是技术上禁止；没有 PR / Git 平台集成。

## 3. `execute_bash` 的超时与资源上限

**行为**

| 项 | 默认 | 配置 |
| --- | --- | --- |
| 超时 | 180 秒；模型可以在参数里要更长，最多 1800 秒 | `AGENTGO_SHELL_TIMEOUT_SEC`（0 = 不设默认上限） |
| 内存上限（一条命令的所有进程共用） | 物理内存的 70% | `AGENTGO_SHELL_MEM_MB`（-1 自动，0 不限，正数为 MiB） |
| 同时存活的进程数 | 256 | `AGENTGO_SHELL_MAX_PROCS`（0 不限） |
| 输出 | 每路最多保留 8 MiB，头尾各一半，中间标明丢了多少字节 | 常量 |
| 异常崩溃 | 不弹 Windows 错误报告窗口 | — |

- 超时的命令退出码记为 124，输出里带 `[timeout] ...`，模型能看到。
- 取消或超时会结束**整棵**进程树；命令正常结束时，它有意启动并留下的程序（比如开发服务器）不会被杀（`Detachable`）。
- 内存和进程数上限只在 Windows 生效（Job Object）；超时和进程树回收在所有系统上生效。
- Win7 不支持嵌套 Job Object：如果 AgentGo 本身已经在某个 Job 里，命令会在没有上限的情况下照常运行（`BestEffort`），并在日志里写一行。
- 同一套启动逻辑（`internal/shellcmd.Run`）也用在了终端面板（`internal/terminal/exec.go`）和沙箱的本地实现（`internal/sandbox/local_seam.go`），输出同样有上界。

**验证**

- 自动化：`go test ./internal/shellcmd/`（约 37 秒）里的限额测试是真让内核来执行的：内存上限真的让失控分配失败，进程数上限真的让后续进程创建失败，超时真的杀掉整棵树，孤儿进程占着输出管道时不会卡住。另有 `internal/tools` 的 shell 测试、`internal/bridge/shell_limits_test.go` 和架构测试（进程启动必须隐藏控制台窗口等）。
- 真实模型（终端版，临时数据目录，`AGENTGO_SHELL_TIMEOUT_SEC=3`）：让模型运行一条要跑约 20 秒的命令（`ping -n 21 127.0.0.1`）。模型先用 `tool_search` 找到 `execute_bash`，停在审批上（`-yolo` 自动放行），命令只跑了 3 秒就被结束，工具返回退出码 124 和 `[timeout] ... larger timeout_seconds` 的提示，模型原文转述了这两样；全程 12 秒，结束后系统里没有残留的 `ping` 进程；临时数据目录（含配置副本）已删除。
- 没有用真实模型验证内存上限和进程数上限，这两项只有上面的内核级自动化测试。

**一个原有的行为，要知道**：默认的"助手 + 平衡"模式下，`execute_bash` 对模型是不可见的（`internal/agent/mode_policy.go` 的 `AllowsDynamicTool` 明确排除了它）。第一次真实模型测试就是栽在这里：模型搜了五次都搜不到，如实回答"没有这个工具"。要让模型能执行命令，需要把执行深度切到"深度"（或管理员模式；终端版用环境变量 `AGENTGO_EXECUTION_CANVAS=deep`）。这是原有设计，这次没改；意思是资源上限只对开放了命令行的模式有意义，办公室同事默认用的模式碰不到它。另外 `execute_bash` 在任何模式下都要审批，`-yolo` 也是由终端版自动点同意，不是跳过审批。

## 6. 打包与打包后复验（`0.1.0-win7.10`，2026-10-28）

**产物**（`bin\`）：`agentgo-0.1.0-win7.10-windows7-amd64.zip`（网页版，21.7 MB）、`agentgo-0.1.0-win7.10-wails-windows-amd64.zip`（桌面版，22.5 MB），各带 `.sha256`；`AgentGo-win7.exe`、`AgentGo.exe` 是同一份 exe 的解压副本。压缩包里的 exe、`SHA256SUMS.txt`、`.sha256` 文件和打包日志里的哈希两两核对一致；`README.md` 含新建文件、指令文件、命令上限三段新说明；`build-info.json` 记录版本、构建时间、源码提交 `bc0d806` 和"工作区有未提交改动"。

**复验**（网页版 exe，临时数据目录，真实模型 `qwen/qwen3.7-max`；脚本放在临时目录，用完删除了数据目录和配置副本）

| 检查 | 结果 |
| --- | --- |
| 版本戳 | `GetAppInfo` 报 `0.1.0-win7.10`，`host=web`，`tags=web`，Go 1.27.2（旧工具链） |
| 工作区外的文本文件，拒绝 | 弹 1 次审批，拒绝后模型没读到内容 |

要点：
- 办公电脑上"读工作区外的文件"是能用的，前提是用户在审批卡上点"允许"；授权只在本次运行内有效（重启 AgentGo 要重新批准），按文件夹放行，同一文件夹里的其他文件不再问。拒绝则不会读取。
- 不需要审批的例外：用 `@完整路径` 提及的文本文件，AgentGo 在发消息时直接把内容贴给模型；二进制文档（xlsx、docx 等）只贴一个指引，之后模型再读还是要走审批。
- 永远不放行：`..` 穿越、盘符根目录、系统目录、凭据目录、AgentGo 自己的数据目录；"严格"模式完全不允许离开工作区。
- 数据目录里的 `AGENTS.md` 和（将来的）`hooks.json` 属于用户级文件，不受工作区限制。
