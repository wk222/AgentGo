# AgentGo 与 OpenBitFun 差距分析（2026-10-27）

目标：保留 AgentGo 的核心特色，把「每天放心用」所需的短板补齐，并且说清楚哪些差距是有意不补的。

## 结论先行

1. 两个项目定位不同。OpenBitFun 是联网的个人/开发者工作台：跨设备接力、技能和小应用市场、皮肤、SSH/容器远程工作区。AgentGo 面向公司内网办公电脑（含 Windows 7）：单个 exe、不依赖联网和 Office、办公文档、逐次可审计的审批。逐项追平 OpenBitFun 不是目标。
2. 真正影响日常使用的短板集中在「看得见」和「出了事找得到原因」：用量看不见、日志不轮转、崩溃没有现场、版本号查不到、会话不能改名和导出、权限档位只能改配置文件、中文记忆搜不到。这些本轮全部补齐，并在真实浏览器里用真实模型跑过。
3. 跨设备、市场、皮肤、语音、电脑控制、远程工作区这类差距**有意不补**：内网没有中继服务器，Win7 和单 exe 的约束，以及这类能力的安全面都不适合办公电脑默认带上。理由见后文。
4. 仍然存在的真实短板（数据库没有版本校验、没有会话归档/分叉、MCP 没有管理界面、Win7 没有实机验证、exe 未签名）列在最后，带优先级。

## 怎么比的，以及边界

- OpenBitFun 一侧来自 OpenBitFun 仓库（本机克隆）的 README、`docs/interactive-capabilities` 能力目录和 `src` 目录结构。**没有运行它**，所以只对比"有没有这类能力"，不对比体验和稳定性。
- AgentGo 一侧来自代码和真实运行。真实运行用的是公司网关上的 `qwen/qwen3.7-max`，在浏览器版里实际对话、审批、导出、看用量、生成诊断包。
- 开发机是 Windows 11，没有真实的 Windows 7 机器，Win7 浏览器版只验证到"用 legacy Go 工具链能编过并通过测试"。

## 要保留的核心优势

这几条不要为了「追平」而削弱。

1. **内网和老机器能用**：浏览器版不需要 WebView2，legacy Go 工具链编给 Windows 7，所有资源编进一个 exe，不依赖联网。
2. **治理和审批**：每次改文件、运行命令、访问工作区外的文件夹都要在审批卡上点「允许」，并且有永不放行的目录；开放模式也只是少问"工作区里改文件"。
3. **记忆有证据链**：来源引用、可信度、不自动置顶、撤回即归档，现在还能看见。
4. **办公文档**：不装 Office 就能做 Excel、PPT、Word，改 Excel 前自动留备份。
5. **内部应用与工作流**：把重复流程做成工具或应用，创作中心管版本。
6. **企业通道**：飞书、微信、企业微信。

## 有意不做，以及原因

| 项 | 原因 |
| --- | --- |
| 跨设备、中继、手机和手表 | 内网没有可部署中继的服务器；把办公电脑上的智能体暴露给其他设备，安全面太大 |
| Skill / Mini App 市场、皮肤市场 | 需要联网和运营；内网用创作中心自给 |
| 用户可配置 Hooks | 等于让普通用户在办公电脑上配置自动执行的脚本；等有明确需求再做，并且要走审批 |
| SSH / 容器 / WSL 远程工作区 | 办公场景是本机文件；远程执行要凭据管理，风险高 |
| 浏览器控制、桌面控制、Computer Use | 对办公电脑风险过高，不适合默认带上 |
| 语音、桌宠 | 与办公文档主线无关；语音要引入识别和合成模型，体积和 Win7 兼容都是问题 |
| 脱机派发到服务器 | 没有服务器 |
| Git 的 PR 评审、worktree | 办公用户基本不用；开发者场景才需要 |

## 仍然存在的短板和优先级

**P1，下一轮最值得做**

1. **Win7 实机验证。** 构建和测试都过了，但没有在真实 Win7 + Chrome 109 上走过一遍。
2. **exe 未签名。** 办公电脑的杀毒软件可能拦截或误报，需要找信息科做白名单，或者购买代码签名。这一条是风险提示，没有在真实办公环境里验证过。
3. **会话归档与分叉。** 用久了侧栏会很长；现在只能删除或搜索。

**P2**

4. MCP 管理界面（至少能看到已连接的服务和工具、能启停）。
5. Windows 系统代理（现在只认环境变量里的代理）。
6. Git push / pull。
7. 用量页增加费用估算（需要各模型单价，由用户填）。

**P3**

8. `web_fetch`。9. 数据迁移和一键备份。10. 删除没有调用方的 `internal/memory/visualize.go`（依赖外部 CDN）。

- `go test ./... -count=1` 全部通过，没有失败。
- `go test -tags web ./... -count=1` 55 个包全部通过（发布脚本用的就是这组）。

### 打包后的复验（0.1.0-win7.8）

- 发布脚本（legacy Go 1.27.2）对两个包各跑完整测试：浏览器版（`-tags web`）55 个包通过，桌面版 55 个包通过，前端 35 项通过。
- 桌面版第一次跑时，`TestNativeLSPToolsAgainstGopls` 失败：三个包并行的高负载下，gopls 冷启动超过 30 秒初始化期限。单独跑 2.5 秒通过，改成两个包并行后全绿。这说明电脑很慢或杀毒软件正在扫描时，代码工作区的语言服务可能初始化失败，只影响诊断、跳转这类代码工具，不影响对话和办公文档。
- 打包后的真实 exe（临时数据目录）：
  - 桌面版：启动 12 秒不崩，窗口和侧栏正常渲染，WebView2 子进程正常，关窗干净退出，`crash.log` 为空；日志在没有控制台时写入 40 行（修复前是 0 行）。
  - 浏览器版：`GetAppInfo` 报告版本 `0.1.0-win7.8`；诊断包 10 个条目；真实模型对话触发 `code_grep`，在 `internal/codetools` 里搜到新加的两处 `HideWindow`，行号对得上。
  - 库来自更新版本：桌面版弹出「AgentGo 无法启动」，退出码 1；浏览器版退出码 1 并打印原因；两者都没有改动那个库（版本号、日志模式、已有表和数据原样）。
- 这一轮由真实 exe 才暴露的问题：桌面版日志为空、子进程黑窗、启动失败无提示。单元测试和浏览器版都没有发现，因为它们都有控制台。

## 经验教训与下一步

- **浏览器版有控制台，会掩盖桌面版的问题。** 日志为空、子进程闪黑窗、启动失败静默，这三个都是只有在 GUI 子系统里才出现的。以后每次打包后，至少要对桌面版 exe 做一次不重定向输出的启动检查，并看 `agentgo.log` 有没有内容。
- **验证用的数据目录必须真隔离。** 这台电脑的数据目录由 `adrg/xdg` 决定，认的是 `XDG_DATA_HOME`；只改 `LOCALAPPDATA` 隔离不了，程序会直接用真实目录。验证脚本要同时设置 `XDG_DATA_HOME`、`LOCALAPPDATA`、`APPDATA`，并在启动后核对日志里的 `data_dir=`，不对就立刻结束进程。
- **只跑受影响的包会漏掉全局规则。** `cmd/*` 只允许依赖 `bridge`，这条由架构测试在全量测试里才会发现；改了 `cmd` 或新增依赖后必须跑完整测试（发布脚本会跑）。
- **构建机磁盘不能满。** C 盘只剩约 20 MB 时，链接阶段会报 `There is not enough space on the disk`。本次清理了一份 12 GB、早已没人引用的 Go 构建缓存。`C:\Users\user\AppData\Local\Temp` 里还有成批的 `vscode-stable-user-x64-*` 目录，约 2 GB，可以自行清理；建议把 TEMP 移到 E 盘。
- **并行度。** 这台电脑上桌面版发布脚本用 `-TestParallelism 4` 时，gopls 测试会超时；用 2 稳定。
- **下一步（按价值排序）：** 在真实 Win7 办公机上跑一遍（最大的未验证项）；评估给 exe 做代码签名，减少杀毒软件误报；会话归档与分叉；MCP 服务管理界面和 Windows 系统代理；`web_fetch` 工具与备份/迁移按钮。
