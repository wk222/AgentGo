# AgentGo 对照 WeKnora：吸收建议

日期：2026-10-28。依据两个本地工作目录的源码，包含未提交改动；只做静态审阅，未运行应用、测试或真实模型评测。本文补充现有 `weknora-pageindex-digestion-plan.md`，不改变其已确认决定。

## 结论

AgentGo 应保留本地优先的统一智能体运行时，吸收 WeKnora 的文档证据工程。优先打通“解析 → 结构化块 → 检索 → 本轮证据 → 引用原文 → 更新失效”，再决定是否增加文档树、Wiki 和数据源。

不能仅按功能名称判定差距：AgentGo 已有 Eino、混合召回、RRF、记忆摘要树、插件生命周期、审批、任务中心和大结果外置。WeKnora 的相应实现不应再形成第二套运行时。

## 现有基础与具体缺口

| 项目 | 源码事实 | 含义 |
| --- | --- | --- |
| 分块 | `internal/docchunk` 已注明源自 WeKnora，具备结构保护、标题路径、父子块和 rune 偏移；`bridge/chunker_plugin.go` 挂接 `memory.SetChunker(svc.Chunk)` | 已吸收算法；当前记忆钩子的返回类型为 `[]string`，不能传递结构元数据 |
| OCR | `internal/visionocr` 已有 provider、VLM 和输出清洗；原方案记录真实网关识别质量未验证 | 继续验收，不能把“包已移植”计作真实办公文档质量提升 |
| 解析 | `tools/docparser.go` 的输出是 Text、Pages、FileType 等；PDF/DOCX/XLSX 解析后拼接文本 | 尚无统一的逐块页码、工作表行号、原文版本契约；Pages 取解析文档条数，需按 parser 语义验证 |
| 召回 | `memory/recall_graph.go` 与 `recall_merge.go` 已有多路召回和 RRF；`recall_hybrid.go` 回查 SQLite 的当前状态和 scope | 不应重复移植 RRF，也不能说 AgentGo 完全没有陈旧结果防护 |
| 输出预算 | `agent/spill_middleware.go` 将大结果保存并提供预览和回读工具 | 已解决部分体积问题；仍可增加按结果结构生成的模型视图 |
| 评测 | `evaluation/retrieval.go` 已支持 Hit、Recall、MRR、nDCG 和耗时 | 复用现有评测入口，增加证据、更新失效与总成本指标 |
| 桌面 | 当前 `cmd/agentgo/main.go` 导入 `agentgo/frontend` | 旧记录中的 frontend-legacy 已不适合描述当前工作目录 |

## 按收益排序的吸收方向

### P0：保留来源结构，交付可核对的引用

借鉴 WeKnora 的 `internal/types/source_locator.go`、`internal/sourceloc`。先实现文本范围、PDF 页、Excel 工作表与行范围，坐标高亮后置。

建议新增中立的数据契约：`DocumentRevision{document_id, content_hash, parser_version}`、`Chunk{chunk_id, revision, text, heading_path, parent_id, locator}`。具体归属包需遵循现有架构守卫，避免 memory 反向依赖具体插件。

文档接入必须保留结构化块；现有 `[]string` 记忆钩子继续服务旧调用方。偏移须明确是 rune、字节还是 token，不能在规范化/OCR 后拿新文本偏移直接套旧原文。无法可靠对齐时显示位置未知。

验收：回答中的引用能打开正确版本的正确页/行；中文、重复段落、跨页表格和部分映射都有用例。

### P0：借鉴 modelcontext 的“本轮证据资格”

WeKnora 的 `internal/modelcontext/README.md`、`sources.go`、`citations.go` 将导航句柄与本轮引用资格分开：历史引用可用于导航，但须重新读取才成为当前执行的证据。

AgentGo 可由统一模型调用边界维护执行级来源注册表，给模型短引用句柄；调用工具前解析回稳定 ID，并继续经过现有路径授权和治理。短句柄不能成为权限凭证。引用资格只证明出处被读取，不证明回答被出处支持，仍需内容验收。

验收：伪造句柄、跨会话句柄、历史未重读引用均不能变成有效的新证据；完整输出和流式输出行为一致。持久化使用稳定 ID，恢复后重建注册表。

### P1：工具结果按结构生成模型视图

借鉴 `modelcontext/model_output.go` 与 `agent/tools/output_budget.go`：完整结果用于存储、UI 和回读；模型视图按记录预算，保留来源、关键字段、摘要、遗漏数量与回读入口。这层应先于通用 spill，spill 继续兜底。

先覆盖文档检索、批量表格、MCP 结果。不要把新协议铺满所有工具，也不要直接把 WeKnora 的类型体系搬进来。

验收：批量结果中间的记录不会因整串截断消失；预算内保留每条最小摘要，并测量后续回读次数、总输入 token 与总耗时。

### P1：补文档版本与衍生数据失效

借鉴 `types/knowledge.go` 的处理状态，以及 `application/service/knowledge_delete_plan.go` 的清理组织方式。原文、块、索引、摘要树、派生记忆都要能追溯版本。

先实现幂等导入和更新版本切换：新版本可用后切换有效版本，旧任务不得把旧结果重新发布。现有 SQLite 回查机制保留，并扩展文档版本校验。原文删除后，引用保留历史说明但不可默认为当前有效证据；已提炼个人记忆的处理需区别独立确认事实与仅来自文档的归纳。

验收：更新制度文件后只引用新版；删除源文件、取消后重试、并发导入和旧任务晚完成不会恢复失效内容。

### P2：按需求吸收数据源同步，评测后再上树检索

`datasource/connector.go` 的增量游标和流式 checkpoint 值得借鉴。先做用户选定的本地目录、单文件刷新；已有内网需求时再选一种平台接入，调度复用 taskhub/scheduler。

现有方案 D2 的文档树保留为可选路线。先以相同语料、查询和预算比较 SQLite FTS、现有混合召回、结构化分块+邻块读取，树检索作为候选。不能预设“不用向量”更优，也不能用三份长 PDF 的结果代表整个办公场景。

## 对已有方案的调整建议

保留 D0、D4a 及按能力组装策略。D1 扩为“结构化来源 + 版本 + 引用”；把执行级证据注册、模型结果视图、版本失效放在 D2 文档树前。D2 由固定施工项改为评测后决定。OCR 与 DOCX/XLSX 的来源定位不应等到 PDF 坐标高亮阶段才考虑。

不建议整搬租户/RBAC、Wiki/图谱服务、独立 Agent loop、数据库/队列基础设施或另一套桌面壳。WeKnora 本身已有 Lite 和桌面路线，不能简单断言它只能重部署；不整体引入的理由是产品域和现有状态所有权重叠。

建议第一批只交付：一份 PDF 和一份 XLSX 的结构化解析、检索、引用跳转、修改后失效。确认这个闭环后，再扩大格式和数据源。

代码复用继续沿用 `licenses/weknora` 的许可与归属记录；每个新增移植文件注明来源。

## 2026-10-29 复查：剩余值得吸收的机制

本节重新核对当前本地源码；HEAD 定位为 WeKnora 59c1805、AgentGo bc0d806，结论包含工作目录代码，不能当作上游最新版或干净提交的对比。本次只审阅和更新计划，没有新功能实现或新的质量评测结果。

此前 A/B/C/D 的实现与验收边界见 [实施记录](weknora-implementation-2026-10-28.md)；主聊天执行归属的最新进展见 [Runtime 记录](eino-runtime-integration-2026-10-22.md)。RRF、普通文本去重、召回预算、来源快照和显式文档版本切换均已有实现，不再列作缺失能力。

### 1. 优先补向量空间身份与维度校验

WeKnora 的 knowledgebase_search.go 将模型名、端点、配置维度纳入查询向量复用身份，并检查实际返回维度。AgentGo 的 hybrid.go 当前向记忆 metadata 写入 embedding 数组；embeddings.go 读取该数组做相似度，长度不同返回零，未见随该写入保存并校验模型空间身份。同维度换模型也不能说明向量可比。

建议借鉴其身份/校验机制，在现有 embedding metadata 保存空间指纹、维度与内容版本；不匹配或缺少身份的旧向量不参加相似度排序，保留 FTS 并给出诊断。若确需重建，复用现有任务机制，不建第二套索引平台。这是根据源码提出的 AgentGo 设计，不代表 WeKnora 已实现这里描述的全部旧索引迁移策略。

验收：同维度换 embedding 模型、返回维度漂移、旧元数据和原文更新均不能静默混排；不为身份检查新增模型调用。聊天模型 ID 不应误当 embedding 空间身份。

### 2. 让文档结构穿过存储和召回，再做邻块补读

WeKnora 的 chat_pipeline/merge_expand.go 按同一文档查前后块；merge_overlap.go 仅在坐标可信、文本吻合时按范围合并，编辑/改写内容改走文本校验，避免重复表格行被误删。

AgentGo 的 parse_file 已返回结构化父子块和定位；但 chunker_plugin.go 的记忆接线仍是 memory.SetChunker(svc.Chunk)，learn_document 的版本化学习分节主要保存 source/revision/generation/section，尚未把解析器的页/行定位、父子块和邻块关系完整贯穿这条学习召回链。已有图邻居、摘要树和文本去重不能替代这一闭环。

建议先扩展现有文档来源记录的元数据，由一个实际文档召回消费者读取；只对文档块做同来源、同版本、同权限的有限邻块补读，再决定是否合并。个人原子记忆继续保留自己的语义。不要先造通用知识库服务。

验收：跨页条件与结论、相邻重复表格行、编辑后旧偏移、跨文档相似段落、删除后的邻块均有固定用例；同预算比较当前召回、补读和重排，成功率没有改善就不启用新策略。

### 3. 本地文件刷新借鉴同步游标与安全删除核对

WeKnora 的 datasource/connector.go 将逐项 ingest 与完整可恢复 cursor checkpoint 结合；Emit 失败停止抓取，Checkpoint 必须是完整快照。值得吸收的是恢复协议，不是整套平台连接器。

AgentGo 当前 learn_document revision 对应供给文本，不是已核验的磁盘文件哈希；文件改动仍需要显式重读并 replace。可先做用户选定目录的一次“刷新”：按实际读取内容计算版本，复用已有 CAS 与 taskhub；成功处理一项才记录进度。完整扫描成功后才能核对删除，不能把扫描失败/权限错误当文件被删除。目录常驻监听、飞书/Notion 等连接器后置。

验收：处理中断后重试不重复学入，扫描失败不误撤回，旧任务晚完成不重新发布，工作区切换不串源。

### 4. 借鉴同数据集的检索/生成联合评测组织

WeKnora 的 evaluation.go 将检索指标与生成指标放在同一评测流程；其 GenerationMetrics 主要为 BLEU/ROUGE，不能据此宣称验证了事实支持。

AgentGo 已有 Hit/Recall/MRR/nDCG 和产物任务评测。真正要补的是小型办公闭环套件：给定文档→检索→回答→引用原文→修改/删除→再次提问。复用 evaluation，检查引用版本、证据支持、无答案时的行为，以及整个任务的模型调用、回读次数和耗时。引用存在/能打开与结论被原文支持分开打分，语义判断须有人工或经过验证的评审，不用关键词命中冒充事实正确。

先固定 12–20 个 PDF/XLSX/中文制度问答任务并记录基线，再决定邻块、rerank 或问题扩展是否值得引入。此套件尚未创建/运行，不是已取得的能力提升证据。

### 5. 条件项：批量结果按条分预算

WeKnora 的 agent/tools/output_budget.go 使用公平分配，wiki_tools.go 用它缩短各条大正文，避免整串截断丢掉中间记录。AgentGo 的 parse_file 模型视图已减少重复定位数据并保留全部块，通用 spill 也已存在，不能重复实现这两层。

只有在批量文档/MCP 等第二类实际结果出现中间条目丢失或反复全量回读时，再扩展现有模型视图：每条保留身份、最小摘要和回读句柄，剩余预算分给正文。以“答案落在中间条目”的固定任务比较总 token 与完成率；更贵或效果无改善就保留原行为，不铺到所有工具。

### 执行顺序与不吸收项

先完成既定的治理预算/调用跟踪状态归属，再补向量身份正确性和小型办公基线；有基线后推进文档结构闭环与选定目录刷新。批量预算、独立 reranker、FAQ 相似问法/生成问题仅按实际失败案例选择，不同时开工。

执行进度：治理预算/调用跟踪已在同日后续实现，状态归入现有审批 SQLite，并删除旧内存预算/跟踪器；见 [执行记账记录](eino-runtime-integration-2026-10-22.md)。本节列出的向量身份、办公基线与文档召回增强尚未实施。

暂不吸收 Wiki 平台、图谱基础设施、多租户/RBAC、第二套 Agent 编排和新增浏览器执行层。浏览器只在固定任务证明确实需要登录/JS/交互后评估；静态网页仍走已有 search→web_fetch。本地工作区、可核对证据、扩展工具与统一运行时继续是 AgentGo 主线。

## 2026-10-29 追加：非 RAG 机制

此前列表偏文档证据，本节单独审阅工具接入、技能执行、交付和运行质量。仍以当前本地源码为准；未启动 WeKnora，也未执行以下故障场景，发现与建议均不冒充已验证的能力提升。本节发现的 MCP 契约问题应先于新增检索功能处理。

### N1 / P0：MCP 工具身份、风险与重载契约

WeKnora 的 agent/approval/mcp_risk.go 区分服务声明、已观察风险和工作区明确策略，风险不能仅因服务后来声称只读就自动下降；modelcontext/mcp.go 集中处理服务/工具路由身份。声明只是信号，不应替代本地授权。

AgentGo 在 tools/registry.go 中把映射键写成 server_tool，却直接存入 Eino MCP 工具对象。本地已安装的 eino-ext/tool/mcp v0.0.9 的 Info 返回原始工具名，RPC 也使用原名，因此映射名和模型声明名确实没有由这一接线统一。多服务同名工具存在冲突风险。重载同名服务会关闭旧客户端并加入新工具，但这段重载路径没有先移除旧 summary.Tools，已撤掉的远端工具可能留在注册表中，直到显式卸载。这里是源码发现，尚未以两台实际 MCP 服务复现。

同时，该接线没有把服务工具声明映射到 AgentGo 已有 tools.Spec/ToolTraits；仅接上 MCP 不等于已纳入完整的风险元数据契约。SDK 已处理 isError 并序列化完整结果，不重复造一套 MCP 错误解析器。

建议只扩现有 Registry/Spec：包装统一模型可见名称且保留远端原名；绑定服务来源/定义版本/风险；重载做完整替换、退役旧工具与连接。验收：两服务同名工具各自调用正确，移除的工具不再可见，声明改变不绕过审批，已有调用不会静默路由到新定义。

### N2 / P1：失败止损和“执行结果未知”

WeKnora 的 agent/engine.go、failed_tool_loop_test.go 按工具名与参数跟踪相同失败，达到阈值后只注入一次改换方案的提示；mcp/errors.go 将执行结果未知与明确执行前拒绝分开，后者才可能安全重试。

AgentGo 刚完成的调用限额统计到失败尝试，但粒度是每工具的速率/循环计数；tool_heal 已明确不在实际调用后自动重试，这部分保留。可再针对相同规范化参数、相同失败补充策略引导；网络断开导致结果未知时，让模型/UI 明确看到“先查状态”，而非普通失败后重复提交。复用已有根运行与治理记录/Eino 中间件，不搬 WeKnora 的 Agent loop。

验收：连续同参失败会换方案，换参数后的合理修复不被全局锁死；发送/写入后断线不自动重放。WeKnora 的 stream_retry_partial_test.go 还值得作为故障用例借鉴：重试成功应替换失败尝试的半段文本；先核对 AgentGo 的现有流协议再决定是否改实现。

### N3 / P1：Skill 的执行准备与凭据注入

WeKnora 的 agent/skills 区分轻量元数据、按需正文、资源文件、shell 运行环境和每次执行的 EnvResolver；缺少必需配置可返回有类型的错误，保留宿主定义的输入/输出环境变量。

AgentGo 已有技能发现、activate_skill、脚本执行/生成能力。skills.Loader 当前主要按文件夹和首段提取元数据；值得补的是发现→激活→执行准备之间的契约：规范元数据、可用解释器/依赖检查、工作目录、输入/产物目录、缺失配置诊断。继续走现有 sandbox/进程治理，不新建技能运行时，不自动安装依赖。

凭据只用引用名参与技能选择，在实际调用边界解析进受控环境；不把 secret 值塞进技能正文或模型参数。WeKnora 的部分交互提示允许让模型收集 env 值，该交互不照搬。先复用 AgentGo 的私有配置与现有配置治理，不为此建设多租户秘密管理平台。

### N4 / P1：真实任务产物的交付与版本

WeKnora 的 application/service/artifact_collector.go 从已有沙箱收集输出，限制 I/O，并按路径/mtime 与内容 hash 判断是否新增；不清空输出目录。types/message_artifact.go 的删除 tombstone 防止已删文件再次自动挂回。filetransport 只传输已经获授权的文件，授权仍由调用方决定。

AgentGo 已有办公文件工具、附件、MediaRef/FileBlock 和扩展产物版本；它们不能自动等同于通用任务输出的交付闭环。可把“生成了某个文件”变成真实文件检查→归属当前运行/会话→登记内容版本→界面下载/打开→重启后仍可访问。复用已有文件/会话/资源接口，先支持一种任务输出，不另建文件云盘，也不扫描整个工作区把无关文件附给用户。

验收：未落盘路径不形成成功交付；内容未变不重复挂载；原地改写产生新版本；用户删除后不自动复活；新版本和旧下载引用不串档。生成文件存在不代表文件内容正确，仍需格式/业务验证。

### N5 / P1：Agent 操作产品功能时复用真实业务入口

WeKnora 的 agent/operations/catalog.go 从 API 声明收窄可执行操作，并经真实路由复用身份、校验与审计。可借鉴的是同一业务入口和能力白名单，不是给每次本地操作增加一次 HTTP 请求。

AgentGo 已有 Spec、capability.Bus、扩展目录及工作流/内置应用工具；优先检查 IPC、工具、扩展目录是否对同一能力使用同一业务实现和风险声明。按一个真实管理操作做一致性验收，再决定是否扩 Spec 的投影/校验，避免新增一个平行 operations 平台。保留本地运行时与可生成扩展的特色。

### N6 / P2：可解释的请求级调试

WeKnora 的 agent/act.go 同时记录 model_arguments、resolved_arguments、解析状态和真实工具结果；modelcontext 将编解码放在一个边界，Langfuse 只观察。敏感工具缩减字段，不能将可观察性变成凭据泄露。

AgentGo 已有 ContextInspector、HTTP 最终请求 dump、模型 usage 校准、治理审计和统一 run_id；不需要再搭日志平台。应补的是按 run_id/call_id 串起模型原始参数、修复后实际参数、策略决策、结果、压缩前后视图、估算与实际用量，直接在现有调试界面解释“为何没调用/为何拦截/为何成本高”。受控脱敏与显式启用优先于全量落盘。

### 浏览器与自动化的定位

浏览器也有非 RAG 借鉴点：WeKnora 的 approval/page_action.go 使用有 request/tool-call/session 身份的页面读填请求，限时等待，页面不响应即失败，不留下悬空等待。若 AgentGo 出现操作已有登录页的实际任务，可先接这种窄协议，再评估完整浏览器自动化。当前无需加入另一套 browser-use 框架。

WeKnora 的 automation/trigger.go 还提供时区、一次性时间和 cron 的统一校验；AgentGo 已有 scheduler/trigger/taskhub，先做现有入口的时间语义一致性验收，不重复增加自动化中心。
