# 大工具输出与往返次数（2026-10-17）

问题：怎样让大工具输出少占上下文、让模型少绕几趟。结论先行：**在现有评测负载上，这块几乎没有可省的东西；真正可省的是往返次数。**

## 现状

- `SpillMiddleware`：工具输出 ≥6KB 或 ≥50 行时落盘，消息里换成头 12 行 + 尾 5 行 + `fetch_spill_content` 提示。取回只支持行号区间和正则。
- 记忆召回（`internal/memory`）已有 BM25 + RRF，但 spill 取回没用上。

## 度量（`spilled` / `saved_bytes`，见评测报告）

`RunMeter` / 网关 `usage` / `agentgo-eval` 现在记录 `spills`、`spilled_bytes`、`saved_bytes`。只有"真的被预览替换"才计数。它一上线就查出：

1. **spill 对文件读取完全不起作用。** `read_workspace_file`、`search_workspace`、`run_batch_script` 的结果都是**一整行 JSON**（正文里的换行是转义的 `\n`），按物理行数判断只有 1 行，预览函数原样返回。默认套件里一次真正的替换都没发生。
2. **同一份输出每次模型调用都重写一遍磁盘。** 旧代码先落盘再生成预览，预览没替换原文，下次调用又写一份。现在先用真实预览长度判断，省不到 512 字节就不写（`spillWouldShrink`）。

## 一次失败的尝试（A/B 否决，已撤销）

让单行大输出也能被字节预览截断。子集（6 个会读 `compile.go` 等大文件的用例，各 3 次，同模型）：

| 版本 | prompt token | 工具调用 | 缓存命中 |
|---|---|---|---|
| 修改前 | 316,319 | 45 | 83% |
| 字节预览（撤销） | 565,802（+79%） | 83 | 74% |
| 现行（只记度量 + 不重复落盘） | 308,348（-3%） | 43 | 92% |

模型要读的文件内容本身就是答案，截断后它只能反复调 `fetch_spill_content` 翻页，而该工具的偏移按行算，对一整行 JSON 毫无意义。**文件读取不能当噪声输出落盘。**

## "按意图一次取回"值不值得做

设想：`fetch_spill_content` 增加 `query` 参数，按 BM25 返回最相关的段落，代替"看预览、猜行号、再取"。

先看真实工具输出的形态（`AGENTGO_DUMP_LLM_DIR` 抓请求体）：

| 场景 | 工具 | 输出大小 | 说明 |
|---|---|---|---|
| 在目录里搜字符串 | `search_workspace` | 1.2 KB | 一整行 JSON |
| 跑一条会出长输出的命令 | `run_batch_script` | 174 B | **模型自己在脚本里过滤，只打印结果** |

典型任务里工具输出本来就小，模型会把过滤写进脚本。要让 spill 触发，需要三步：①展开 JSON 信封、按真实行落盘；②把文件读取排除在外（上面已证明）；③构造一个"必须完整输出再检索"的用例——而这种用例本身就是人为的。

**判断：现在做按意图取回，在评测里测不出收益，却要改 spill 触发条件和工具 schema（影响所有请求的前缀）。不做，除非先出现真实的"大输出撑爆上下文"的案例。** 如果出现，最小方案是：`fetch_spill_content` 加 `query`（纯 spill 包内改动，BM25 分块，约 150 行加测试）+ 对 shell/搜索类工具展开 JSON 后再判断是否落盘，并且必须过上面那组 A/B。

## 真正可省的：往返次数

`fix-bug-run-tests` 一次修复约 13 次模型调用，其中 `TaskCreate`×2 + `TaskUpdate`×4 是任务记账，占近一半（之前 balanced 档 12 步上限被撑爆就是这个原因）。可做的事：

1. 简单任务（≤3 步）不建任务清单——提示词 / 工具描述改动，必须用评测证明不退化再合入。
2. 批量工具并行调用（模型一次发多个读取）——看评测里并行比例。
